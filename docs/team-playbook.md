# 3人での進め方

> **2026-09-20：Codexを3つ並行で動かす間の担当ファイル・開始手順・AIへの依頼文は [3人で並行作業するとき](parallel-work.md) にあります。** 下の役割表は維持します。

これはチーム内の仮案です。公式日程・条件は [イベント確認メモ](event-brief.md) を参照してください。3人ともハッカソン・共同開発が初めてで、コーディング経験はほぼありません。あなたが広く関わる前提で、専門職ごとの分業ではなく、確認する範囲と小さな作業を分けます。

## 今回の方針

**1人の利用者の、1つの困りごとを、最初から最後まで解決するデモを作る。** 初日に一通りつなぎ、以後は価値・使いやすさ・安定性を高めます。主な利用場面と動作確認に使う入力を先に決めます。

- 必須機能は最大3つ。追加案は後回しの一覧に置く。
- デモの流れは「入力 → AI等の処理 → 役立つ出力」の1本を中心にする。
- 3人が使い慣れた技術を優先し、環境構築に詰まったら構成を簡単にする。
- 初日は価値の成立を左右する処理を早く試す。実現できない場合は対象・入力・機能を絞る。
- 最終日は説明と動作確認に集中できるよう、前日に提出できる状態にする。

## 大まかな役割

役割は「その分野の相談先」。全員が企画・実装・レビューを行えます。3人ともリポジトリに参加済みです（@0k4c、@Murakami-1124、@tomoyan2312）。B・Cがどちらかは最初の打ち合わせで決め、表のB・Cを実名へ置き換えます。

| 人 | 主に見ること | 初日の担当 | 後半の担当 |
| --- | --- | --- | --- |
| A：あなた（0k4c） | 全体の調整と、動くものをつなぐ | 運営条件・要件を整理し、AIと一緒に最小の動作例を作る | 優先順位、統合・起動、共通設定、提出。全体に広く関わる |
| B：メンバー2 | 利用者の目線・入力・使いやすさ | 困りごとの具体例、入力サンプル、画面のラフを用意 | AIと入力画面・説明文を改善。初見で使えるか試し、デモ操作を担当 |
| C：メンバー3 | 出力・確かめ方・伝わる説明 | 期待する結果と、失敗してほしくない例を用意 | AIと結果表示・エラー表示を改善。動作確認、比較結果、発表資料を担当 |

全員がAIを使います。B・Cも実装できますが、最初は文章・サンプル・画面の一部分など、動作を目で確認できる変更から始めます。Aが全部書く必要はありません。B・Cは互いの操作確認とPR確認も受け持ちます。AI処理や認証など全体に影響する変更は、Aが窓口となって3人で確認します。

画面のない作品ならBは入力方法、Cは出力の見やすさを担当します。役割は固定の評価ではなく、得意な作業が分かったら入れ替えます。

## 5日間の到達点

[ロードマップ](roadmap.md) に日ごとの目標と、遅れた場合に減らすものをまとめています。日程はそこを更新し、各タスクの最新状態はGitHub Issuesで管理します。

9/19の公式キックオフ終了後に行う打ち合わせです。11:30開始なら12:30終了。休憩が必要なら3人で開始をずらします。

| 経過 | やること | 残すもの |
| --- | --- | --- |
| 0〜10分 | 運営条件・提出期限、各自の可動時間、役割を確認 | 制約と窓口 |
| 10〜25分 | 各自1案。「誰が、何に困り、どう楽になるか」を話す | 最大3案 |

| 35〜45分 | 必須機能3つ以内・今回やらないこと・成功例を決める | 最小完成形 |

集合時間・運営条件は [キックオフシート](kickoff-sheet.md)、作るものの決定は [短い要件定義書](requirements.md) に書きます。新しいアイデアが出ても、選定を何度もやり直さず、実現性の検証結果を理由に方向を変えます。

## 日々の合わせ方

- 各日の作業開始時に10分：今日見せるもの・担当・依存関係を確認。
- 終了前に15分：実際に動くものを見せ、残りと翌日の最優先を決める。
- 30分詰まったら共有：「試したこと／結果／手伝ってほしいこと」。
- 連絡はDiscord、タスクと決定の記録はGitHub Issue・この資料へ。AIのチャット履歴だけに重要な決定を残さない。
- 同時に着手するタスクは1人1つを基本にし、他の人を待たせる変更を先に共有する。
- 意見が割れたら10分で比較し、担当窓口が理由を記録して暫定案を決め、次のデモで確かめる。追加支出や役割の大幅変更は3人で合意する。

## AIを使う共同開発

**企画・要件・日程・進捗管理はClaude Code、コーディング・テスト・修正はCodexに依頼します。** [AIの役割と引き継ぎ](ai-roles.md) に担当範囲と依頼の形式をまとめています。A・B・C全員が両方のツールを使えます。

最初の環境構築とブランチ・PRの練習は、3人で画面共有して行います。Git操作に慣れるまでは、各自のAIへ下の指示を渡します。各自のcloneと作業ブランチを使い、同じPCで複数のAIを動かす場合だけworktree等で分けます。1つの作業フォルダを複数AIで同時編集しません。

共通設定・依存関係・AIとの接続処理はAが窓口となり、作業者を1人決めます。BとCは先にサンプル入出力を共有し、最小の動作例ができた後に、重ならないファイルの小さな改善へ進みます。待ち時間はサンプル・画面ラフ・確認項目を準備します。

実装時にCodexへ渡す指示の例：

```text
AGENTS.mdと担当Issueを読んで作業してください。
私は共同開発初心者です。現在のブランチと変更を確認し、mainを最新にしたうえで、
他の人の変更を保持して専用の作業ブランチを作ってください。
目的：
変更してよいファイル：
入力と期待する出力（具体例）：
完了条件：
今回やらないこと：
既存の他メンバーの変更を保持し、確認した方法と結果を報告してください。
最後に変更したファイルと手動で試す手順を説明し、Draft PRを作ってください。
マージは別メンバーの確認後に行います。
Issueの状態は変更せず、実装結果をClaude Codeに返せる形でまとめてください。
```

小さなPRを出し、別メンバー1人が差分と動作を確認してSquash mergeします。初日の途中から何度か統合し、mainで動くことを確かめます。AIが「完成」と言っても、操作と結果を人が確認するまで完了扱いにしません。詳細は [CONTRIBUTING.md](../CONTRIBUTING.md)。

## 完成の判定と発表

チーム内の完成条件：主な利用場面が動く／空入力や処理失敗を扱える／別メンバーが手順どおり起動できる／秘密情報を含まない／AIの効果と限界を説明できる。

評価項目を意識して、次の証拠を用意します。これはチームの準備案であり、公式の配点や必須提出物ではありません。

| 見せたい点 | 用意する証拠 |
| --- | --- |
| 価値 | 対象者の困りごとと、使う前後の比較。実測と仮説を区別 |
| 技術・品質 | AIが担う処理、採用理由、同じ入力での動作、失敗時の扱い |
| 独自性 | 既存のやり方と異なる1点。未調査の優位性は断言しない |
| チームワーク | 3人の貢献と、レビュー・統合で改善した箇所 |
| 発表 | 課題 → デモ → 効果 → 工夫と限界の順で説明 |

持ち時間が分かったら配分を決め、デモを中心に通し練習します。Aは課題と全体像、Bは操作、Cは結果と限界を説明する仮分担とし、短時間なら発表者を絞り、他の2人は操作・質疑を担当します。技術説明はAIに下書きしてもらい、実際に作った動作と一致する部分だけ話します。

予備録画は通信不良への備えです。録画・固定データ・実際のAI出力を混同させず、運営の発表ルールに従います。ソース公開が必要と言われた場合もPrivate設定を自動で変えず、審査員の招待等で対応できるか確認します。
