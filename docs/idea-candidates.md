# 制作案の候補：業務を自律化するAIエージェント

作成：2026-09-19（Claude Code）。正式テーマ発表後の**たたき台**です。決定ではありません。
3人で1案を選び、決めた内容は [企画書](proposal.md) と [要件定義書](requirements.md) に書きます。この文書は候補置き場として残し、選ばなかった案は「なぜ選ばなかったか」を1行だけ足します。

## 前提：テーマの公式な分解

Day1資料で、テーマが4つの部品に分解されています。ここは推測ではなく資料の内容です。

| 部品 | 資料の説明 |
| --- | --- |
| モデル | 判断する頭脳。差し替え可能かで5日目の伸びしろが変わる |
| ツール | 外部API・DB・社内システム。エージェントが「実行する」手足 |
| ループ | 結果を見て次を決める繰り返し。**いつ止めるか**まで設計する |
| 記録 | 誰が、何を、いくらで。運用・改善・監査の前提 |

そして「**業務を自律化」＝ ①判断する ②実行する ③記録する を人からAIへ移すこと**、と定義されています。
モデルと記録はOrcaRouterが引き受けるので、**私たちが考えるのはツールとループ**、という整理でした。

審査は5項目×10点＝50点。資料の言葉では次のとおりです。

1. **セキュリティ**：情報漏洩や不正操作への対策が設計されているか
2. **コストパフォーマンス**：品質と利用コストを適切に最適化できているか
3. **信頼性・堅牢性**：想定外の入力やエラーでも安定して処理・復旧できるか
4. **自律性**：状況を判断し、必要なツールを選んで遂行できるか（「決め打ち」でないか）
5. **アイデア・独創性**：「既存の作業をどれだけ置き換えたか」ではなく「**AIに何を任せたか**」

資料には「**自律性が上がるほど、セキュリティと堅牢性の要求は跳ね上がる**」とも書かれています。5項目は独立ではありません。

## この5項目から逆算して、どの案でも必ず入れる設計

案を選ぶ前に、共通で持つ骨格をここで決めておきます。案が変わってもこの骨格は変わりません。

| 審査項目 | 必ず入れるもの | プレゼンで言う一言 |
| --- | --- | --- |
| 自律性 | 許可された次の行動をAIが選ぶ（tool calling）。終了を提案でき、ステップ数・時間・費用の上限はコードが強制する | 「状況に応じた行動をAIが選びます」 |
| セキュリティ | LLMへ送る前に個人情報をマスク。取り消せない操作（送信・確定・削除）は人の承認かドライラン | 「AIに実行させない操作を先に決めました」 |
| 信頼性 | 失敗時のfallbackモデル、リトライ上限、ループ上限、壊れた出力の再要求、途中から再開 | 「3回失敗したら人に回します」 |
| コスパ | ルールで片付く処理はLLMを呼ばない。簡単＝安いモデル／難所だけ強いモデルへ昇格 | 「1件◯円、LLM呼び出しを◯%削減しました」 |
| 独創性 | 「AIに何を任せたか」を1文で言える | （案ごとに違う） |

**記録**は最初から作ります。1件ごとに「処理ID・必要最小限の入力要約・AIが選んだ行動と簡潔な説明・使ったモデル・トークン・概算費用・結果」を残す。秘密情報・個人情報は除去し、入力全文は無条件に保存しません。
確認結果と結び付けると、審査項目の説明材料になります。過去の実行結果は後から復元できない場合があります。

## 前回作品から参考にすること

共有された23リンクのうちFollowUp AI・HRper・KYAKUMAPの3記事を確認しました。設計の要点と全リンクは [前回作品の参照メモ](previous-projects.md) にあります。全48作品の傾向を確認したものではありません。

そのうえで、今回のテーマは「エージェント（ループ・ツール実行・記録）」だと資料で明示されています。
単純な1問1答だけでは、状況に応じて行動を選ぶ箇所を示しにくくなります。自律性の得点を断定せず、何をAIに任せたかを具体例で説明します。

今回、避けたほうがよい形：

- 1問1答で終わるもの（ループがない）
- 画面はきれいだがAIが何も選んでいないもの（手順がコードで固定されている）
- OCR・音声認識・認証・決済が成功の前提になるもの（3.5日で沼になり、落ちたとき何も残らない）

## 候補5案

先に全体像です。実現性は「3人・実質3.5日・ハッカソン初参加」を基準にした私の見立てです。

| # | 案 | AIに任せる判断 | 実現性 | 独創性 | デモの映え |
| --- | --- | --- | --- | --- | --- |
| 1 | 差し戻しまでやる受付エージェント | 受理か、差し戻しか、人に上げるか | 高 | 中 | 高 |
| 2 | 止まった仕事を動かす進行管理エージェント | 誰に、いま、何を聞くか | 高 | 高 | 低 |
| 3 | 自分で検算するデータ整備エージェント | 直していいか、人に聞くか | 最高 | 低 | 中 |
| 4 | エージェントの見張り役（監査官） | 止めるか、モデルを下げるか、人を呼ぶか | 中 | 最高 | 中 |
| 5 | 一次対応と引き継ぎのエージェント | 自分で答えるか、聞き返すか、回すか | 高 | 低 | 中 |

### 案1：差し戻しまでやる「受付エージェント」（推奨）

**業務**：申請・提出物の受付チェック。対象は差し替え可能です（経費精算、補助金・助成金の申請、シフト希望、入社書類、イベントの入稿データなど）。

**AIに任せること**：受け取ったものを「**受理する／差し戻す／人に上げる**」のどれにするかの判断と、差し戻すときの文面。
いまは人が規程を見ながらやっていて、差し戻しの文面を書くのが面倒で後回しになる、という困りごとを想定しています。

**ループ**：受け取る → 中身を読む → 規程と照合 → 不備があれば「何が足りないか」を具体的に書いて差し戻す → 再提出をもう一度判定 → **最大3往復で人へエスカレーション** → 受理したら台帳に記録。

**ツール**：提出物の取り込み（フォーム or ファイル）、規程の検索、台帳への書き込み（SQLite または CSV）、通知（Discord Webhook）。

**止める条件**：受理した／3往復した／根拠や必要情報が足りない。3往復の上限はコードで強制し、AIの自己申告した確信度だけでは確定しない。

**5項目の取り方**：
- セキュリティ：氏名・口座・金額はマスクしてLLMへ。受理の**確定だけは人のボタン**。
- コスパ：必須項目の有無・日付・金額の桁はコードで検査し、LLMは判断が要る箇所だけ。
- 信頼性：同じ提出物を2回投げても二重登録しない。LLMが壊れたJSONを返したら1回だけ再要求。
- 自律性：3つの行動をAIが選ぶ。差し戻しは最大3往復の範囲で判断する。

**デモ（4分に収まる形）**：3件まとめて投入 → 1件は即受理、1件は差し戻し→再提出→受理、1件は人へエスカレーション。最後に台帳とコスト表を見せる。

**一番難しいところ**：規程の書き方。曖昧な規程だとAIの判定がぶれます。先に規程を10行くらいの箇条書きで固定してください。
**縮小案**：往復を1回だけにする／対象を1種類の申請に絞る。

### 案2：止まった仕事を動かす「進行管理エージェント」

**業務**：チームのタスク進行。**このハッカソンの運営そのもの**を対象にできます。

**AIに任せること**：「**誰に、いま、何を聞くか**」。催促するか、分割を提案するか、依存を解く質問をするか、何もしないか。
人間がやると気まずくて先延ばしになる判断です。ここが「AIに何を任せたか」の答えになります。

**ループ**：定期起動 → GitHub IssuesとPR、チャットを読む → 停滞の原因を分類（担当不在／前提待ち／大きすぎる／単に忘れている）→ 行動を選ぶ → 実行（コメント・通知）→ 返答を見て次を決める。

**ツール**：GitHub API（Issue・PRの読み取りとコメント）、Discord Webhook、時刻。

**止める条件**：1日あたりの通知上限、同じ課題への連続催促の上限、人によるミュート。

**5項目の取り方**：
- セキュリティ：書き込みは**コメントだけ**。CloseやmergeはAIにさせない。トークンは権限を絞る。
- 信頼性：同じ催促を二度出さない（送信済みの記録を見る）。API失敗時は次の起動まで待つ。
- 自律性：「何もしない」を選べることが大事。毎回通知するならただのcronです。

**強み**：自分たちの実データで動く。準備するサンプルが要らない。「このエージェントが、この5日間の私たちを実際に動かしました」と言える。
**弱み**：**画面が地味**。ログ画面（誰に・なぜ・何を送ったか）を作らないとプレゼンで伝わりません。

---

### 案3：自分で検算する「データ整備エージェント」

**業務**：汚れた名簿・在庫表・売上CSVの整備。

**AIに任せること**：「この列は何か」「この値は直していいか、人に聞くか」。

**ループ**：検査 → 修正案 → 適用 → **もう一度読み込んで検算** → 不合格なら方針を変えて再試行（最大N回）→ 残りは質問キューへ。

**ツール**：CSV読み書き、郵便番号・住所の照合、差分レポート生成。

**5項目の取り方**：
- コスパ：同じ入力を全件LLMで処理する場合と比べ、**1 − 実際の呼び出し数 ÷ 比較対象の呼び出し数**で削減率を測る（比較対象が0なら算出しない）。呼び出し数と総費用は別々に示す。他の案でも同様の比較は可能。
- 信頼性：自己検算があるので、堅牢性の説明が一番しやすい。
- セキュリティ：原本は書き換えず別ファイルに出す。個人情報はマスクしてLLMへ。

**強み**：実現性が最も高く、数字が出る。3人が並行で作りやすい（検査・修正・レポートに分解できる）。
**弱み**：**独創性が弱い**。似た発想が他チームにも出ます。「自己検算ループ」と「人への質問キュー」を前面に出さないと埋もれます。

### 案4：エージェントの見張り役「監査官」

**業務**：AIエージェントを業務に入れた後の運用管理。誰が何にいくら使ったか、危ない操作をしていないか。

**AIに任せること**：他のエージェントの実行ログを読んで「**このまま続けさせるか、安いモデルに下げるか、止めて人を呼ぶか**」。

**強み**：独創性が高い。OrcaRouterのRequest LogsやGuardrailsと正面からかみ合うので、**OrcaRouter賞（10万円）を狙える**。
**弱み**：監査される側のエージェントも自作する必要があり、実質2本作ることになります。3.5日では重い。
**成立させるなら**：案1〜3のどれかを先に作り、その上に監査画面を載せる順番にしてください。最初からこれを本命にはしないほうが安全です。

---

### 案5：一次対応と引き継ぎのエージェント

**業務**：問い合わせの一次対応。

**AIに任せること**：「自分で答える／足りない情報を聞き返す／人に回す」の三択。

**差別化できる点**：人に回すときに、**要約・根拠・まだ確認できていないこと**を添えること。
**弱み**：発想が一般的で、前回作品にも近いものがありそうです。上の1点を核にできないなら選ばないほうがよいです。

---

## 私の推し：案1、迷ったら案3

**案1**を推す理由：判断・実行・記録の3つが全部入り、5項目のどれにも自然に答えられ、デモが4分に収まります。差し戻し→再提出→受理という往復は、見ただけで「AIが自分で回している」と伝わります。

ただし、**9/19中に「AIが1回判断して結果を返す」ところまで届かなかったら、範囲の縮小や案3への切り替えを検討します**。案3も事前の試作確認が必要で、確実に動くという保証はありません。

**案2**は、もし発表の物語を最優先するなら強い選択です。ただし見せ方を作り込む担当が1人必要になります。

## 決め方（30分で終わらせる）

推測で埋めず、この順で3人で決めてください。

1. 各自が候補から1つ選び、選んだ理由を1文（5分）
2. 分かれたら、次の2つだけで比べる（10分）
   - **9/19中に最小の1本が通るか**
   - **「AIに何を任せたか」を1文で言えるか**
3. 対象業務を1つに固定し、サンプル入力を3件その場で作る（10分）
4. 決めたことを [要件定義書](requirements.md) に記入し、この文書に選定理由を1行足す（5分）

サンプル入力が3件作れない案は、その場で作れないだけの理由があります。避けてください。

## 決まったあとに最初にやること

順番が大事です。上から順に。

1. OrcaRouterのクレジットを3人とも受け取り、`base_url` を差し替えた**5行のコードで1回応答を得る**（全員）
2. 1件の記録が残る形（入力・選んだ行動・モデル・トークン・概算費用・結果）を先に作る
3. その上で、AIに行動を選ばせる（tool calling）
4. 最後に画面

3と4を先にやると、記録が後付けになり、コスパと信頼性の証拠が出せなくなります。
