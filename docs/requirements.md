# 要件定義：ユーザーフレンドリーなAIシフト管理サービス

状態：**主目的はユーザー確認済み（2026-09-21）、詳細仕様と提出範囲はレビュー中**。正本となる方針は [Issue #11](https://github.com/0k4c/ai-hack-2026/issues/11)、全体の概要は [企画書](proposal.md) を参照してください。

従来の「代打手配のみを主目的とする」「シフト表の自動作成は対象外」「画面は記録閲覧・承認だけ」という扱いを改めます。以下の中心機能は目指す要件であり、実装済みという意味ではありません。詳細変更はこの文書と担当Issueに残します。

## 目的と利用の流れ

**従業員の勤務希望を取り込み、AIの支援でシフト案を作成し、管理者が画面で確認・修正・確定できるサービス**を作ります。想定利用者は小規模店舗の店長・シフト管理者です。希望の整理と調整の負担軽減を目指しますが、削減効果は未検証です。

1. 従業員、対象期間、必要人数、勤務条件を設定する。
2. 希望を取り込み、日付・時間・勤務可否を整理する。あいまいな解釈を人が修正する。
3. 条件に沿うシフト案を作り、不足・重複・勤務制約の問題を示す。
4. 表を見て調整し、再検証した結果を確認して人が確定・保存する。
5. 確定後の欠勤には代打手配で対応する。

正式テーマ「業務を自律化するAIエージェント」に対して、AIは希望の解釈や案の作成・調整を支援します。勤務条件の検証はコードが行い、最終確定は人が行います。案作成でのAIと割当ロジックの具体的な分担は実装Issueで定義します。

## 中心機能の入出力と完了条件案

新しいIDは S1〜S3 とします。既存Issueの F1〜F3 は欠勤対応の候補選定・再打診・記録画面を指す旧IDであり、中心機能の完成を意味しません。

| ID | 入力と利用者の操作 | 出力・完了条件案 | 現在の実装との差分 |
| --- | --- | --- | --- |
| S1：条件と希望の準備 | 画面で従業員・対象期間・必要人数・勤務条件を設定し、希望を取り込む | 日付・時間・勤務可否を確認・修正できる。不明点と不足入力を具体的に示し、修正内容が作成に使われる | 希望文のAI解釈は既存。条件設定・取り込み・修正の画面と保存は必要 |
| S2：シフト案作成と検証 | S1で確認した希望と条件から作成を実行する | 対象期間のシフト表を出す。人数不足、勤務の重複、連勤・週労働時間などを検出し、該当日・時間・従業員と理由を示す。充足できない枠を隠さない | 表全体の生成は未実装。既存の候補用制約判定を、期間全体の割当に適用できるよう設計する |
| S3：確認・修正・確定 | 表を見て割当を修正し、人が明示的に確定する | 修正後に条件を再検証し、提案と確定済みを区別する。確定した表を保存して再表示できる。失敗を確定成功と表示しない | 表の編集・確定画面と保存は未実装。欠勤対応のローカル承認は別機能 |

これらは実装タスクを作るための完了条件案です。対象期間・勤務枠・厳守する条件と調整できる希望の区別を決めてから、具体的な入力例と期待結果を各Issueに記載します。

### ユーザーフレンドリーさの基準

- 希望の取り込みから表の確定まで、主な操作を画面で進められる。利用者にCLIやJSON編集を要求しない。
- 現在の段階と次に行う操作を表示する。空入力・処理中・失敗・完了を区別する。
- AIの解釈と提案を人が確認・修正できる。不足・矛盾を該当箇所と理由で示す。
- 条件を満たせない案やAI通信の失敗を、完成した勤務表として扱わない。
- 表の修正・確定方法、画面幅などの具体的なUI仕様は担当Issueで定める。

### 写真読み込みと画像出力

当初の「紙のシフト表の写真を読み込み、各メンバーの希望を取り込んでシフト表を作る」という要望を維持します。画像としての表の出力は「可能なら対応」の要望です。

写真の対象（既存表・希望表）、対応するレイアウト、読み取り誤りの確認方法、提出時に扱う範囲は未確定です。写真読み込みと画像出力は現在未実装です。これらの対応範囲を調整する場合も、シフト作成という主目的を代打手配だけへ置き換えません。

## 欠勤対応：既存機能の位置づけ

確定後に欠勤が発生した際、代打候補を選び、返事を解釈して次の行動を決める補助機能です。作成したシフト表との連携はこれから設計します。

| 部品 | 現在できること・制約 | 根拠 |
| --- | --- | --- |
| 候補選定と希望解釈 | 架空データの勤務条件で候補を絞り、AIが候補を選定。希望文の日付・時間の解釈も可能 | PR [#10](https://github.com/0k4c/ai-hack-2026/pull/10)、[#13](https://github.com/0k4c/ai-hack-2026/pull/13) |
| 再打診と停止・記録 | 返事をAIが解釈し、最大3巡・全体180秒で停止する。送信はdryrun、返事は架空JSON。実送信はない | PR [#21](https://github.com/0k4c/ai-hack-2026/pull/21) |
| 記録画面・ローカル承認 | 記録を確認し、人の操作でこのPCに承認を保存する。表全体の編集・確定機能ではない | PR [#29](https://github.com/0k4c/ai-hack-2026/pull/29)、[#33](https://github.com/0k4c/ai-hack-2026/pull/33) |
| 承認の不整合 | CLIと画面の保存先・判定が異なり、二重承認が可能。未解決として扱う | Issue [#34](https://github.com/0k4c/ai-hack-2026/issues/34) |

欠勤対応の3巡・180秒という上限を、未実装のシフト表生成の上限にそのまま転用しません。生成処理の時間・試行回数・費用上限は、対象規模と方式が決まった段階で定義します。

## 権限・データ・信頼性

- AIに勤務の確定操作を与えない。入力文中の指示を承認として扱わない。
- 勤務条件の検証をAIの返答だけに任せず、生成後・修正後・確定時にコードで検証する設計とする。
- デモには架空データを使う。現在のシードは従業員6人。実在の個人情報やAPIキーをコミットしない。
- 既存処理は氏名を従業員IDへ置換してAIへ送る。新しい希望・画像入力で送る情報と保持方法は実装前に整理する。
- AI・通信・保存の失敗を明示し、提案と確定済みのデータを混同しない。モデル・判断・利用情報を追える記録を残す。
- 費用の欠損値は0円と扱わない。応答で得た概算費用と確定請求額を区別する。モデルの比較結果は [モデル比較](model-comparison.md) を参照する。
- 設定した連勤・労働時間の上限を検証しても、労務法令への準拠を保証したとは扱わない。

## 詳細化が必要な項目

| 項目 | 決める内容 |
| --- | --- |
| 対象規模 | 対象期間（週・月など）、人数、店舗数 |
| 勤務枠 | 時間の粒度、日またぎ、必要人数を指定する単位 |
| 条件 | 必須条件と希望の区別、休憩・役割・資格など今回扱うもの、割当できない場合の確定可否 |
| 希望の取り込み | テキスト・写真等の対応形式、確認画面、未提出や不明な希望の扱い |
| 確定と保存 | 修正履歴、再編集、同時更新、欠勤対応とのデータ共有、保存方式 |
| 利用環境 | 対応ブラウザ・画面幅、ローカルデモとサービス運用の範囲 |
| 外部連携 | 実送信、認証・権限管理、給与・勤怠連携は現在未実装。今回の提出範囲に含めるかは別途判断 |
| 提出範囲 | 写真読み込み・画像出力を含む実装範囲、担当、日程、計測・デモ条件 |

## 確認するケース案

S1〜S3の実装時に具体的なサンプルを決めて検証します。以下は未実行の受入確認案です。

- 希望・必要人数を取り込み、案作成、修正、確定、再表示まで画面だけで進められる。
- あいまいな希望は自動で確定せず、修正した内容が生成に反映される。
- 人数不足・重複・連勤・週労働時間の問題を検出し、理由を示す。手修正後も再検証される。
- 満たせない条件、空入力、不正なAI出力、通信失敗、保存失敗を成功と表示しない。
- AIが「承認済み」と返しても勤務が確定しない。人の操作で確定した内容だけが保存される。
- 別メンバーが初見で主要な流れを操作し、不明な操作・説明を記録する。
