# 簡易要件定義：AIシフト管理サービス

2026-09-21更新。ユーザーの要望とIssue [#39](https://github.com/0k4c/ai-hack-2026/issues/39)〜[#63](https://github.com/0k4c/ai-hack-2026/issues/63)（25件）をまとめたレビュー用の文書です。**作りたいサービスの要件と、現在実装されている機能は別です。** 未決定事項・追加案は後半に分けています。全体の窓口は [#11](https://github.com/0k4c/ai-hack-2026/issues/11) です。

## 1. どんなサービスか

**複数の店舗・団体がそれぞれ独立して使える、ユーザーフレンドリーなAIシフト管理サービス。** メンバーが自分の画面から勤務希望を出し、AIが入力・確認・シフト案作成を補助します。管理者は不足や矛盾を確認し、表を修正して最終確定します。

目的は、希望の取りまとめとシフト調整の負担を減らすことです。実際の負担削減効果はこれから検証します。欠勤時の代打手配もサービス内の機能ですが、中心はシフト作成・管理です。

## 2. 誰が何をするか

| 利用者 | 主な操作 |
| --- | --- |
| 団体の管理者・シフト作成者 | 団体作成、招待、勤務条件の設定、提出状況と要確認案件の確認、シフト作成・修正・確定 |
| 希望を出すメンバー | 団体に参加、自分の希望入力、AIの質問へ回答、提出・修正、自分の確定シフトの確認 |
| 確認を引き継ぐ担当者 | AIで解決しなかった内容を確認し、結果を本人へ返す。管理者との兼任・担当の割当方法は未決定 |

同じ人が複数団体に所属でき、Aでは管理者、Bではメンバーという使い方に対応します。管理者も自身の希望を提出できます。入口の「管理する／希望を出す」は案内であり、選択するだけで管理権限は増えません。本人確認の方式は未決定です。

## 3. 基本の流れ

1. **団体を準備する**：管理者が団体を作り、メンバーを招待する。各利用者は所属団体と役割に合った画面へ進む。
2. **募集条件を設定する**：管理者が対象期間・必要人数・勤務条件を設定する。提出期限などの具体的な募集ルールは要検討。
3. **希望を出す**：メンバーがカレンダーや文章で入力する。AIが日付・時間・勤務可否を整理する。
4. **曖昧さを確認する**：例えば「夕方なら働ける」に対し、AIが「何時から働けますか？」と短く聞き返す。本人が要約を確認して提出する。
5. **必要なら人へ渡す**：AIとの確認でも解決しない場合、原文・会話・未解決点を担当者へ引き継ぐ。未確定の時間を勝手に勤務可能としない。
6. **シフト案を作る**：管理者が提出状況を確認し、希望と条件から案を作成する。不足・重複・勤務条件の問題を表示する。
7. **調整・確定する**：管理者が表を修正し、再検証して明示的に確定・保存する。メンバーは自分の確定勤務を確認する。
8. **欠勤に対応する**：確定勤務から欠勤対応へつなぎ、人の確認後に変更を反映する。

AI確認が失敗した場合も手入力を使えるようにします。確認回数の上限や人へ渡す条件は実装前に定めます。

## 5. 全画面・全機能で守ること

- **団体を分ける**：希望、勤務条件、シフト、AI会話、画像、処理結果を団体ごとに分離する。他団体の管理者にも見せない。
- **役割を確認する**：本人・所属・権限をサーバーで確認する。団体を切り替えても前の団体のデータを混在させない。
- **人が確定する**：AIの解釈・作成案と、提出済みの希望・確定済みの勤務を区別する。AIだけで勤務を確定しない。
- **問題を隠さない**：未提出、要確認、不足、違反、通信や保存の失敗を成功扱いにしない。再操作・同時更新で二重確定や上書き事故を防ぐ。
- **使いやすい画面にする**：スマートフォンとPCで主要操作ができる。ラベル・エラー・フォーカスを明確にし、状態を色だけで伝えない。
- **指定資料を参考にする**：[デジタル庁デザインシステム](https://www.digital.go.jp/policies/servicedesign/designsystem) と [Material Design 3](https://m3.material.io/get-started) を参照する。特定ライブラリの採用は未決定。
- **確認結果を残す**：AIの利用・費用・失敗、重要な変更を追える設計にする。個人情報の送信・保持範囲は具体化が必要。デモには架空データを使う。

Supabaseは保存・本人確認の候補であり、採用済みではありません。勤務条件を検証することと、労務法令への準拠保証は区別します。

### 6.1 最初に対応する勤務ルールの具体案（#39・未合意）

担当Issueの実装前提を具体化するためのレビュー案です。**下表の採用は未決定で、既存の欠勤対応コードの仕様変更や新機能の実装完了を意味しません。** 本人確認・保存方式は #40・#41 の決定に従います。数値は架空の検証条件であり、実際の勤務規則を定めるものではありません。

| 論点 | 最初の実装に向けた案 | 入力・判定の例 |
| --- | --- | --- |
| 対象期間・時間帯 | 日本時間、月曜〜日曜の1週間。週をまたぐ既存勤務も制約判定に使う | 2026-09-28〜10-04。9/27以前・10/5以降の勤務も連勤判定に必要 |
| 勤務枠 | 管理者が日付・開始・終了・必要人数を指定。30分刻み、同日内、開始より終了が後 | 9/28 18:00〜22:00、必要人数2人。22:00〜翌02:00は未対応として拒否 |
| 勤務時間 | 検証では枠の開始から終了までを勤務時間に数える。休憩の自動控除・分割割当は初回案に含めない | 18:00〜22:00は4時間。架空例は短時間枠で確認する |
| 人数と資格 | 初回案は枠全体の必要人数（1以上の整数）。役割・資格別人数は別途詳細化 | 2人必要で1人しか割り当てられなければ「1人不足」 |
| 勤務可能な範囲 | 本人が明示して提出した勤務可能時間に、勤務枠全体が収まる場合だけ候補にする | 18:00〜21:00のみ可なら18:00〜22:00枠の候補にしない |
| 希望の強弱 | 「勤務不可」は必須条件。「できれば休みたい」は勤務可能な範囲内の希望とし、外れた場合に表示 | 不可の人は割り当てない。希望に反する案は理由とともに人が確認する |
| 未提出・未確認 | 未提出、下書き、AI確認中、人への確認待ちは勤務可能とみなさない | 「夕方なら」は時刻が確定し、本人が提出するまで候補から除外 |
| 週時間・連勤 | 団体内のメンバーごとに上限を設定。既存勤務と今回の案を合わせて判定。同日複数枠は連勤1日 | 検証用に週12時間・連勤3日。上限と等しい場合は許可し、超過は拒否 |
| 重複 | 同じ団体・本人で時間が重なる割当は禁止。終了と次の開始が同じなら重複ではない | 18:00〜20:00と20:00〜22:00は可。19:30〜22:00は前の枠と重複 |
| 提出期限・変更 | 募集時に期限を指定。期限ちょうどから提出・修正を止める案。期限後は管理者が再募集する | 9/25 18:00 JSTが期限なら17:59:59は可、18:00:00は期限後 |
| 作成・修正・確定 | AI案と手修正を同じ条件で再検証。必須条件違反・人数不足がある間は案を保存できても確定できない | 条件を満たせないときは理由と未割当を残し、人が条件や案を直す |
| 団体間の関係 | 希望・条件・勤務は団体内で判定。他団体の勤務や会話を自動で取り込まない | A管理者/Bメンバーの本人でも、BでAの権限・希望を使わない（既存要件） |

公平さの数値目標や希望の重みは未決定です。初回案でも勤務時間と希望に反した割当を表示して人が調整できるようにし、「公平な最適解」とは説明しません。確定と公開の関係、確定後の訂正は #54・#55 で具体化します。

**レビューで決めること**：週単位・30分刻み・日またぎ未対応で開始してよいか、休憩と資格別人数を初回から必要とするか、期限後の再募集と人数不足時の確定禁止でよいか。提出までの採用範囲・納期は人が決め、これらの案を未確認のまま確定仕様として実装へ渡さないでください。

### 6.2 入力と期待するシフトの例（#39・未実装）

以下は6.1を採用した場合の**架空の受入例**です。JSON/API形式は #41 で決めるため、ここでは業務上の入力と期待結果だけを固定した案にします。既存の6人の欠勤対応データは変更しません。

- 団体A、期間2026-09-28（月）〜10-04（日）、提出期限9/25（金）18:00 JST。
- 勤務枠は9/28・9/29のそれぞれ18:00〜22:00、各2人。他の日は募集なし。
- A内の架空メンバー a1・a2・a3 は全員、週12時間・連勤3日を上限とする。期間の前後にも既存勤務はない。
- a1・a2 は両枠の全時間を勤務可能として提出済み。a3 は9/28のみ全時間勤務可能、9/29は勤務不可として提出済み。
- 「できれば休みたい」という希望はこの正常例では指定しない。

| 枠 | 条件を満たす割当の一例 | 判定 |
| --- | --- | --- |
| 9/28 18:00〜22:00 | a1・a3 | 必要人数2人を満たす |
| 9/29 18:00〜22:00 | a1・a2 | 必要人数2人を満たし、a3の勤務不可を守る |

a1は週8時間・2連勤、a2・a3は各4時間・1勤務日となり、条件を満たします。**この組合せだけを正解にしません。** 他の割当も人数・勤務可能時間・週時間・連勤・重複の全条件を満たせば許可します。作成された案は、管理者が確認して確定操作を行うまで未確定です。

下表の各行は、この正常例から別々に変更します。追加勤務の例では管理者が該当時間の枠（必要人数1人）を追加し、a1はその全時間を期限前に勤務可能として提出済みとします。週時間・連勤・重複以外の未提出や人数不足で判定が変わらないようにします。

| 正常例からの変更 | 期待する結果（6.1の採用後） |
| --- | --- |
| a2の9/29を勤務不可に変える | 9/29はa1だけが候補。「1人不足」と表示し、勝手にa2・a3を割り当てず、確定を拒否する |
| a2を未提出に変える | a2を割り当てない。9/29の不足と未提出を別々に表示する |
